# P017 Caption Highlight Support

**Date:** 2026-06-19
**Branch:** `fix/p017-caption-highlight-support` (from `main` @ `ff8bc32`)
**Goal:** narrow follow-up to PR #327 — wire P017 caption findings into the existing
generic highlight pipeline using `CaptionLine.bbox` geometry that already exists but
is currently discarded before reaching `AuditFinding.details`.

## 1. What P017 issue types exist

`check_pdf_captions()` (`src/njit_auditor/rules/pdf_captions.py`) emits exactly four
issue types, determined by `caption.context` (`list_of_tables` / `list_of_figures` /
`body`) and `caption.caption_type` (`figure` / `table`):

| issue_type | caption_type | context |
|---|---|---|
| `unexpected_terminal_period` | table | `list_of_tables` |
| `missing_terminal_punctuation` | figure | `list_of_figures` |
| `missing_terminal_punctuation` | figure | `body` |
| `possible_sentence_case_issue` | figure | `body` |
| `unexpected_terminal_period` | table | `body` |
| `possible_title_case_issue` | table | `body` |

(`toc` and `references` contexts are skipped entirely — no finding is emitted at all,
so they are not a category of "explanation-only" findings; they simply never produce
a P017 finding.)

## 2. Which P017 findings are tied to CaptionLine

**All of them.** `check_pdf_captions()` has exactly one finding-construction site
(line ~211), and it sits inside `for caption in detect_caption_lines(pdf_document):` —
every `AuditFinding(rule_id="P017", ...)` is built from a real `CaptionLine` instance
in scope at construction time. There is no P017 finding that lacks a `caption` object.

## 3. Does each relevant CaptionLine now have bbox

**Yes.** `detect_caption_lines()` constructs every `CaptionLine` with
`bbox=line.bbox` (line ~149), where `line` is the matched `PdfTextLine`.
`PdfTextLine.bbox` is a required (non-Optional) `BBox` field on the Pydantic model —
it is never `None` in practice. `CaptionLine.bbox: BBox | None = None` keeps the
defensive `Optional` type for the class itself, but the only construction site in the
codebase always supplies a real bbox. `CaptionLine.bbox` was added in PR #327 (commit
`f34d450`) to support P020's caption-derived title-case path, and was explicitly noted
in that PR's audit doc as making P017 "incidentally propagation-eligible" — this PR
acts on that note.

## 4. Is page number available

Yes — `caption.page_number` is always set from `page.page_number` and is passed
through as `AuditFinding.page` unchanged.

## 5. Is bbox reliable enough for highlighting

Yes. `caption.bbox` is the exact 1:1 bounding box of the single text line that matched
`CAPTION_START_RE` (the literal "Figure N. ..." / "Table N. ..." line) — the same kind
of precise, single-line, real-geometry box already propagated for P027 heading lines
and P038 heading-phrase lines in PR #327. As with every other rule, the existing
`has_visible_highlight()` predicate is the sole gate for whether a button is shown; an
off-page, zero-area, or otherwise degenerate box (e.g. from unusual PDF extraction)
will simply resolve to no highlight, exactly as designed. This PR does not change that
gate.

## 6. Which P017 issue types remain explanation-only

**None, structurally.** Unlike P019 (where some issue types such as
`missing_page_number` or `multiple_page_numbers` have no candidate object, or have
multiple competing candidates with no single correct one to box), every P017 finding
is built from exactly one `CaptionLine` with exactly one bbox. Any individual finding
can still end up explanation-only at render time if `has_visible_highlight()` rejects
the box (e.g. a genuinely degenerate extraction) — but there is no issue type that is
*designed* to lack geometry. This matches P027/P038/P020/P063's pattern from PR #327
more closely than it matches P019's mixed pattern.

## 7. Rendering path — confirmed fully generic, no special-casing needed

- `report_view._parse_bbox_from_details()` reads `details["bbox"]` generically for any
  rule_id — no P017-specific code required.
- `report_view.build_report_view()`'s presentation dispatch only special-cases
  `category == "page_numbering"`, `rule_id == "P011"`, and `rule_id == "P026"` — P017
  (category `figure_format` / `table_format` / `punctuation`, per
  `evaluation.map_finding_rule_to_category`) hits none of these branches and uses the
  fully generic `_finding_view_from_item` path for `bbox`, `has_highlight`,
  `location_label`, `action_kind`, `action_label`, and `no_highlight_reason`.
- `detailed_explanation` for P017 is built by
  `finding_explanations.build_detailed_explanation()` → `_build_explanation_text()`.
  P017 has no entry in `_EXPLANATION_TEMPLATES` and no entry in `_RULE_FALLBACKS`, so
  it currently falls through to `_GENERIC_FALLBACK` ("This finding was generated by an
  automated formatting check..."). This fallback contains **no hardcoded
  highlight-availability sentence**, so the PR #327 contradiction bug
  (`_margin_detailed_explanation` / `_font_detailed_explanation` unconditionally
  appending "No exact highlight is available...") does not apply to P017 — there is
  nothing to fix in `finding_explanations.py` or `report_view.py`. Confirmed by
  reading both functions in full.
- `line_preview` (the existing raw caption-text detail key) is never read by any
  Jinja template (`grep -rn "line_preview" src/njit_auditor/templates/` returns no
  matches) — confirmed unchanged by this PR, and adding `bbox` does not add any new
  rendered text field alongside it.

## 8. What was implemented

Exactly one change, in `src/njit_auditor/rules/pdf_captions.py`: add
`"bbox": format_bbox_detail(caption.bbox)` to the `details` dict built in
`check_pdf_captions()`, guarded on `caption.bbox is not None` (defensive, matching the
type signature; in practice always true). No other file required a change —
`report_view.py`, `finding_explanations.py`, and `pdf_highlight.py` are all untouched.

This is the narrowest possible diff that satisfies the goal: existing
`has_visible_highlight()` / `sub_page_location_label()` / the `/pdf/highlighted` route
all pick up the new `bbox` value automatically, exactly as they did for P027/P020/P063
in PR #327.

## 9. Privacy

- No new rendered field. `bbox` is consumed only by `has_visible_highlight`,
  `sub_page_location_label`, and the highlight route — never printed as text, exactly
  as established in PR #327.
- `caption.caption_body` / `line_preview` (raw caption text) is not touched, not
  newly exposed, and was already not rendered before this change.
- No raw bbox coordinates are exposed in any student-facing template.

## 10. Risk notes

- No detector threshold, rule ID, canonical rule JSON, or guideline file touched.
- No change to which P017 findings fire, their severity, issue_type, or message text.
- `has_visible_highlight()` still gates every highlight action — this change can only
  ever *add* a highlight action to a finding that previously had none.
- `pdf_highlight.py` not modified.

## 11. Tests added (Phase 6)

New file `tests/test_p017_caption_highlight_support.py` (13 tests, 7 parametrized
cases), covering all eight required categories:

1. P017 with valid caption bbox — real highlight, `/pdf/highlighted` returns 200 with
   a modified PDF containing a real annotation, explanation text still rendered
   (parametrized over all four P017 issue types: `missing_terminal_punctuation`,
   `possible_sentence_case_issue`, `unexpected_terminal_period`,
   `possible_title_case_issue`).
2. P017 without bbox — stays explanation-only: no highlight button, no
   `/pdf/highlighted` link, no `"Open PDF page"`/`"Open first example page"`,
   explanation text unchanged.
3. Invalid/degenerate bbox safety — zero-area, inverted, and NaN bbox strings all
   resolve to `has_highlight=False` with no crash; a manual highlight request for the
   same job/rule/page falls back to the plain PDF (200, not 500).
4. Caption privacy — raw bbox coordinates and the raw `line_preview` caption text
   never appear in rendered HTML; `location_label` never contains coordinates.
5. PR #327 regression — P011 highlight coverage still works when mixed in the same
   job as P017 findings.
6. Forbidden-action regression — `"Open PDF page"` and `"Open first example page"`
   never reappear (the legitimate whole-document `"Open PDF"` button, distinct from
   these forbidden strings, is correctly excluded from this assertion).
7. Mobile/desktop parity — identical highlight-button counts, identical
   `/pdf/highlighted` link sets, and identical explanation/location-label text under
   mobile vs. desktop headers, for both the highlighted and non-highlighted P017 case.
8. No-500 route crawl — main, category, rule, issue-type, and highlighted-PDF routes
   for a job containing all four P017 issue types (mixed bbox/no-bbox) plus a P011
   control finding.
